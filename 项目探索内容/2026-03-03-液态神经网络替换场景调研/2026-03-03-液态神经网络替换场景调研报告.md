## 3. 可替换性总览

| 模块 | 当前实现 | 是否建议液态替换 | 推荐模型 |
|---|---|---|---|
| 主对话 LLM | 云端 LLM + tools | 否（不直接替换） | 保持现状/路由优化 |
| 人格 PAD 动力学 | 规则 + 衰减 + 阈值锁定 | 是（高优先级） | CfC / LTC |
| 执行门控（auto/blocked） | 阈值二元门控 | 是（高优先级） | CfC |
| 端侧表情/动作时序 | 关键词触发 + timer | 是（高优先级） | NCP |
| 语音/视觉并发调度门控 | 规则状态机（规划中） | 是（中高优先级） | NCP / CfC |
| 文本情绪分类主干 | NLI + ONNX int8 | 部分替换（中优先级） | CfC 平滑头 |
| 意图筛选器 | 多语言规则+解析 | 不建议整体替换 | 规则为主，模型重排可选 |
| Mem0/摘要 | 检索与压缩 | 否 | 非 LNN 适用域 |

## 4. 高优先级替换场景

## 4.1 人格 PAD 动力学引擎（优先级 P0）

现状问题：

1. 参数多且人工调参成本高。
2. 锁定/解锁等边界行为依赖阈值与手工公式。
3. 需要更平滑、可学习的时序响应。

建议替换点：

1. 保留 `SoulEmotionState` 数据结构与 MQTT 协议不变。
2. 在 `engine.go` 内引入模型后端（`rule` 与 `lnn` 双实现）。
3. `Update()` 里通过特征序列推理得到新状态，再映射回原字段。

收益预估：

1. 减少规则膨胀与参数耦合。
2. 对输入噪声更鲁棒，状态变化更连续。
3. 不改接口即可灰度上线。

## 4.2 执行门控（优先级 P0）

现状位置：

1. 聊天主链路中使用 `exec_mode` 决定是否执行：
   [/Users/zhangfeng/Desktop/Linux/DesktopRobot/Soul/internal/orchestrator/service.go](/Users/zhangfeng/Desktop/Linux/DesktopRobot/Soul/internal/orchestrator/service.go)
2. 周期 tick 也依赖同一门控结果：
   [/Users/zhangfeng/Desktop/Linux/DesktopRobot/Soul/internal/orchestrator/emotion_decay.go](/Users/zhangfeng/Desktop/Linux/DesktopRobot/Soul/internal/orchestrator/emotion_decay.go)

建议：

1. 用 CfC 输出 `gate_score`（0~1），再映射到 `auto_execute/blocked`（先保留阈值）。
2. 先仅参与“建议值”，与现规则并行记录，不直接切换执行路径。

## 4.3 Body 端表情动作时序（优先级 P0）

现状问题：

1. 本地意图命中后动作保持时间随机，行为不连续。
2. 与 `emotion_update` 连续输入耦合弱。

建议：

1. 以 `emotion_update` 流作为时序输入，NCP 输出表情状态与持续时长建议。
2. 保留原 `setEmotion()` 接口，先做“推荐动作层”，再逐步接管。

2. 用 NCP 学习“何时中断视觉任务”“何时丢弃 stale 结果”“冷却窗口长度”。

## 5.2 情绪服务规则后处理（P1）

现状：

1. 目前 `emotion-server` 中含较多关键词与规则融合逻辑。

建议：

1. 保留 `mDeBERTa` 主干输出 PAD。
2. 将后处理从规则改为轻量 CfC 时序平滑头，减少规则维护负担。

## 6. 不建议替换场景

1. 主聊天 LLM 整体替换为 LNN：不建议。LNN不擅长通用语言生成。
2. 意图筛选器整体替换为 LNN：不建议。现规则解析可解释性与可控性更高。
3. Mem0 记忆检索替换为 LNN：不建议，问题类型不匹配。

## 7. 与项目当前性能瓶颈的关系

依据：
[/Users/zhangfeng/Desktop/Linux/DesktopRobot/doc/性能探索报告-LLM响应延迟与工具调用影响.md](/Users/zhangfeng/Desktop/Linux/DesktopRobot/doc/性能探索报告-LLM响应延迟与工具调用影响.md)

关键事实：

1. 主耗时在 LLM 推理与工具选择，不在 MQTT/技能执行。
2. 因此液态模型的最大价值在“减少进入慢路径的次数”和“优化实时门控”，不是直接替掉主 LLM。

## 8. 本机部署可行性（2026-03-03）

本机信息：Apple M1，16GB RAM。  
可行结论：

1. CfC/LTC/NCP 训练与推理可本机完成（小中型任务）。
2. LFM2 350M/700M/1.2B 可本机推理（可用于本地路由或轻量对话降级）。
3. 24B 级别模型不建议本机长时部署。

## 9. 推荐实施顺序

1. Phase A（1~2周）：Persona 引擎 `rule + lnn` 双轨，离线回放评估。
2. Phase B（1周）：Body 端 NCP 表情动作控制灰度。
3. Phase C（1~2周）：语音/视觉门控学习策略上线。
4. Phase D（可选）：引入 LFM2.5 作为本地路由层，降低云端调用比例。

## 10. 落地约束

1. 协议不改：保持 `emotion_update`/`intent_action`/`/v1/chat` 兼容。
2. 可回滚：所有替换点使用环境变量开关控制。
3. 先离线再在线：先对历史消息回放验证，再灰度到真实流量。
