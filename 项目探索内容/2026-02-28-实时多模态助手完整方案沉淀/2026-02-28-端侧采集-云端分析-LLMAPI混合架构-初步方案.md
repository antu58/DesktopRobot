# 2026-02-28 端侧采集 + 云端分析 + LLM API 混合架构（初步方案）

## 1. 决策结论（已确认）

后续总体架构统一为：

1. 端侧负责数据采集、轻量预处理与缓存，不承担重推理。
2. 云端（阿里云自建服务）负责语音/视觉分析、融合编排与策略调度。
3. 大模型与视觉大模型通过 LLM API（当前以千问 API 为主）进行重推理。

该文档作为后续可行性设计、接口细化、部署实施的基线版本。

---

## 2. 目标与边界

## 2.1 目标

1. 支持语音与视觉并行输入，语音链路优先，保持低延迟交互。
2. 云端完成 ASR 分段组装、视觉快路径识别、人脸特征库比对、事件融合。
3. 复杂语义理解与生成交给 LLM/VL API，降低本地设备算力要求。
4. 在成本可控前提下，保障稳定运行与可观测性。

## 2.2 非目标（当前阶段）

1. 不在端侧部署完整 LLM/VL 模型。
2. 不在端侧执行大规模人脸库检索或复杂视觉推理。
3. 不做强依赖单机本地 GPU 的旁路方案。

---

## 3. 分层架构与职责

## 3.1 端侧（设备/机器人）

职责：

1. 音视频采集（麦克风、摄像头/截图）。
2. 轻量预处理（VAD、降噪、压缩、节流、去抖）。
3. 断线缓存与重传（环形缓冲区）。
4. 与云端保持长连接（WebSocket 或 MQTT+UDP）。

约束：

1. 端侧不直接调用千问 API。
2. 端侧只上传必要数据与结构化事件，降低带宽。

## 3.2 云端接入层（Ingest Gateway）

职责：

1. 设备鉴权、会话管理、心跳保活。
2. 音频流与帧数据接入、协议转换。
3. 请求限流、重试、熔断与灰度开关。

## 3.3 云端分析层（Analyze Services）

职责：

1. 语音：VAD 分段、ASR、final 组装、语气词/低信息过滤。
2. 视觉：目标检测（YOLO）、OCR、人脸检测与特征向量提取。
3. 人脸比对：向量检索（小库可内存，大库建议向量库）。
4. 事件化输出：`known_person_appeared`、`offer_object`、`risk_event` 等。

## 3.4 云端编排层（Orchestrator）

职责：

1. 多源事件合流（voice/vision/tool）。
2. 优先级调度（`voice > vision`）。
3. 上下文拼装（最小化注入，避免噪声）。
4. 调用模型网关并回传流式结果。

## 3.5 模型网关层（Model Gateway）

职责：

1. 统一封装 LLM/VL API（当前千问 API）。
2. 统一鉴权、超时、重试、回退策略。
3. 记录 token、时延、错误码用于成本和稳定性分析。

---

## 4. 核心数据流（v0.1）

## 4.1 语音主链路（高优）

`端侧音频 -> 云端 ASR 分段/过滤 -> 编排层 -> LLM API -> 云端回传 -> 端侧播放/显示`

规则：

1. 语音回合触发高优先级请求。
2. 视觉任务不得阻塞语音响应。
3. 支持 pre-token 与 post-token 打断。

## 4.2 视觉链路（低优异步）

`端侧帧流 -> 云端快路径识别 -> 事件聚合 -> 按需触发 VL API -> 结果回写上下文`

规则：

1. 仅关键帧/关键事件触发慢路径 VL 推理。
2. 视觉结果设置新鲜度窗口，过期丢弃（stale discard）。
3. 非显式视觉问题时，默认不强行注入每轮对话。

## 5. 协议草案（v0.1）

建议在现有 `llm_request` 扩展：

```json
{
  "type": "llm_request",
  "request_id": "s-xxx-r123",
  "session_id": "s-xxx",
  "trigger_source": "voice|vision",
  "priority": "high|low",
  "text": "你看这是什么",
  "vision_context": {
    "window_ms": 8000,
    "summary": "用户将一朵花靠近摄像头约1.2秒",
    "objects": ["flower", "hand"],
    "ocr": [],
    "known_person_ids": ["p_001"],
    "confidence": 0.91,
    "stale_after_ms": 6000
  },
  "ts_ms": 1700000000000
}
```

返回事件建议增加：

1. `vision_queued`
2. `vision_canceled_by_voice`
3. `vision_skipped_stale`
4. `llm_stream`
5. `llm_response`
6. `llm_error`

## 6. 资源与部署建议（阿里云）

## 6.1 起步配置（单环境）

1. Ingest/Orchestrator：`4c8g`。
2. Analyze（ASR+CV+Face）：建议 `8c32g + 1 GPU`（如 T4/L4 级别）。
3. Redis（队列/会话态）与对象存储（关键帧/日志归档）。

## 6.2 扩展策略

1. ASR、CV、编排、模型网关独立水平扩容。
2. 峰值时优先保障语音链路，视觉自动降采样（如 1fps -> 0.5fps）。
3. 设置模型网关 QPS/TPM 限流，防止成本失控。

---

## 7. 可观测与成本控制

## 7.1 必打指标

1. 语音：首 token 延迟、final 延迟、打断成功率。
2. 视觉：快路径耗时、慢路径命中率、过期丢弃率。
3. 模型：每请求 token、每会话成本、错误率、重试率。
4. 系统：队列深度、CPU/GPU 利用率、连接在线数。

## 7.2 成本控制策略

1. 先快路径过滤再调 LLM/VL API。
2. 视觉仅上传关键帧，默认限制帧数与分辨率。
3. 明确高低优先级队列，低优任务可延迟或丢弃。

---

## 8. 里程碑（建议）

## M1（最小可用）

1. 打通端侧采集 -> 云端分析 -> LLM API -> 回传闭环。
2. 语音链路稳定运行（含 final 组装与过滤）。
3. 视觉快路径可产出结构化摘要并可注入对话。

## M2（稳定增强）

1. 上线优先级调度与打断策略（voice 抢占 vision）。
2. 完成人脸库比对与事件冷却策略。
3. 接入统一观测看板与成本统计。

## M3（体验优化）

1. 视觉异步回执 + 二阶段回复。
2. 精细化策略路由（文本问题不触发视觉模型）。
3. 自动降级（模型超时、配额不足、网络抖动）。

## 9. 当前待确认项（下轮细化）

1. 设备端协议最终选型：纯 WebSocket 还是 MQTT+UDP 混合。
2. 人脸库规模预估与检索技术选型（内存/Faiss/专用向量库）。
3. 千问 API 的并发上限、限流阈值与预算上限。
4. 数据留存策略（原始音视频保留时长、脱敏策略、合规要求）。
